# Зберегти й опублікувати зміни

Розробник ці зміни **не перевіряє**. Тому перед будь-якою публікацією ти сам робиш повну перевірку, а людина явно підтверджує, що саме публікується.

## Крок 1. Подивись, що зберігаємо

- `git status`, `git diff`. Перелічи людині зміни простими словами (2–5 пунктів).
- Переконайся, що в змінах немає `.env`, ключів, паролів, тимчасових і випадкових великих файлів. Таке не додавай і скажи про це.

## Крок 2. Повна перевірка (обов'язково)

1. Форматер, лінтер, typecheck, тести й build проєкту — усе, що є і запускається за розумний час.
2. Проведи рев'ю змін за скілом `review` (із чеклістом `references/review-checklist.md`), без повного звіту людині. Усе з групи «Треба виправити» — виправ до публікації.
3. Якщо проєкт можна запустити — відкрий змінене місце й переконайся, що воно працює.

**Якщо щось із цього впало через нашу зміну — виправ і повтори. Не публікуй зміни з червоними перевірками.** Якщо перевірка падала ще до нас — скажи про це людині одним реченням і не чіпай чуже.

## Крок 3. Обери спосіб публікації

Визнач, як прийнято в цьому проєкті (у такому порядку):

1. **Правила репозиторію:** `CONTRIBUTING.md`, `CLAUDE.md`, `AGENTS.md`, `README` — якщо там написано, як публікувати зміни, роби так.
2. **Немає git або немає віддаленого репозиторію** (`git remote -v` порожній) → режим **«Лише локально»**.
3. **Основна гілка захищена** (push у неї відхиляється, або в репозиторії є обов'язкові перевірки PR) → режим **«Pull request»**.
4. Інакше спитай людину одним запитанням з варіантами:
   - «Зберегти тільки на вашому комп'ютері»
   - «Опублікувати в окрему гілку / pull request»
   - «Опублікувати одразу в основну версію»

   Запам'ятай відповідь до кінця сесії й не питай знову.

### Режим «Лише локально»
- Збережи зміни комітом у поточній гілці (якщо є git). Без push.
- Скажи людині: «Зміни збережено на вашому комп'ютері. Нікуди не відправлено».

### Режим «Pull request»
1. Якщо зараз основна гілка (main/master/develop) — створи окрему (`change/short-description`).
2. Commit англійською у стилі Conventional Commits (`feat:`, `fix:`, `chore:`…), якщо в репозиторії (`git log -10`) явно не прийнятий інший.
3. Push гілки (ніколи `--force`).
4. Створи PR через `gh pr create` (якщо `gh` є й авторизований). Опис: **Що змінено** (простими словами), **Навіщо** (зі слів людини), **Перевірки** (стиль / безпека / доступність / тести — що пройшло).
5. Зливай тільки коли всі перевірки CI зелені: `gh pr checks --watch`, потім `gh pr merge --squash` (або `--auto`, якщо в репозиторії так прийнято). Якщо злиття потребує схвалення, якого людина дати не може, — скажи про це чесно і зупинись.
6. Дай людині посилання на PR і скажи, що зміна опублікована (або що залишилось).

### Режим «Одразу в основну версію»
1. Перед цим — окреме явне підтвердження: «Зміна одразу потрапить в основну версію проєкту (і, можливо, на сайт). Публікую?»
2. `git pull --rebase` основної гілки, повтор перевірок, якщо підтягнулися чужі зміни.
3. Commit (Conventional Commits, англійською) і `git push` (ніколи `--force`).
4. Якщо в проєкті налаштований автоматичний деплой (CI/CD) — скажи, що зміна з'явиться на сайті після нього, і, якщо є `gh`, покажи статус (`gh run list -L 1`).

## Чутливі зміни

Оплата, авторизація, персональні дані, бази даних, інфраструктура, налаштування деплою — перед публікацією окремо поясни людині ризик простими словами й отримай окреме «так» саме на це. Не публікуй такі зміни одразу в основну версію: тільки через pull request з зеленими перевірками.

## Якщо щось пішло не так

- Немає доступу / помилка авторизації — поясни простими словами, що потрібен доступ до репозиторію, і не намагайся його обійти.
- Конфлікт з чужими змінами — не розв'язуй мовчки. Поясни, що за цей час хтось змінив ті самі місця, покажи різницю простими словами й вирішуйте разом.
- Публікація зламала щось після злиття — запропонуй відкотити: `git revert <commit>` + push (не `reset`, не `--force`).
