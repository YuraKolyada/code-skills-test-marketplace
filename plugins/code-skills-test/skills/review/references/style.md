# Стиль коду (коли в репозиторії немає власних правил)

Перший пріоритет — конфіги й сусідній код проєкту. Цей файл — запасний варіант.

## Загальне
- Кодування UTF-8, переноси LF, відступи як у файлі (за замовчуванням 2 пробіли для JS/TS/CSS/HTML, 4 — для PHP і Python).
- Імена — англійською і змістовні: `isSubmitting`, `fetchUserProfile`, не `flag`, `data2`.
- Без закоментованого коду, `console.log`/`var_dump`/`print` для налагодження, `TODO` без пояснення.
- Магічні числа й рядки, що повторюються, — у константи.
- Одна функція — одна задача. Ранній вихід (`return`) замість глибокої вкладеності.

## JavaScript / TypeScript
- `const` за замовчуванням, `let` — коли значення змінюється, ніколи `var`.
- Строга рівність `===`. Опціональний ланцюжок `?.` і `??` замість ручних перевірок.
- TypeScript: без `any` (краще `unknown` + звуження), без `@ts-ignore` без пояснення; типи для пропсів і повернення публічних функцій.
- `async`/`await` з `try`/`catch` замість ланцюжків `.then()`/`.catch()`.
- Булеві змінні й пропси починаються з `is` / `has` / `with` (`isPending`, `hasError`), а не з дієслова (`showModal`, `hideButton`).
- Змінна, що зберігає значення (а не дію), не починається з дієслова: `stepReturnType`, а не `returnToStepType`.
- Назви відповідають тому, що код робить зараз: перейменували чи узагальнили фічу — перейменуйте й її змінні, константи, функції.
- Нативні API браузера й CSS замість сторонньої бібліотеки, якщо нативне рішення простіше.
- Імпорти: спочатку зовнішні пакети, потім внутрішні (якщо в проєкті інший порядок — як у проєкті).

## React / Next.js
- Функціональні компоненти й хуки. Компоненти — `PascalCase`, хуки — `useSomething`.
- Стабільний `key` у списках (id, не індекс масиву, якщо список змінюється).
- Не змінювати state напряму; похідні значення обчислювати, а не зберігати в state.
- Залежності `useEffect` — повні; без зайвих ефектів для того, що можна обчислити під час рендеру.
- Next.js: `next/image` для зображень, `next/link` для внутрішніх переходів, серверні секрети — лише в серверному коді (без префікса `NEXT_PUBLIC_`).

## Vue
- Composition API (`<script setup>`), якщо проєкт його використовує.
- Пропси з типами, події через `defineEmits`, без прямої мутації пропсів.
- `v-for` завжди з `:key`; не поєднувати `v-if` і `v-for` на одному елементі.

## HTML / CSS
- Семантичні теги (`header`, `nav`, `main`, `section`, `article`, `ul`, `p`) і фрагменти `<>` у React замість обгорток-`div`.
- Інтерактивні елементи — лише нативні (`button`, `input`, `a`), ніколи `div`/`span` з `onClick`.

## Тексти для дій із наслідками
- Дія, наслідок якої неочевидний з підпису або незворотний, — з підтвердженням, яке пояснює: що зміниться, кого це зачепить, що залишиться як було.
- Результат, який користувач має комусь передати (нове посилання, код), показати одразу — з кнопкою «скопіювати» / «поділитися», а не лише тихо оновити на місці.
- Класи — за методологією проєкту (BEM / utility / CSS modules). Без інлайн-стилів, якщо проєкт їх не використовує.
- Кольори, відступи, шрифти — з існуючих змінних/токенів (CSS variables, Tailwind theme), а не нові «магічні» значення.
- Адаптивність: mobile-first, перевіряти ширини 375px, 768px, 1280px.
- Без `!important`, якщо без нього можна обійтися.

## Node.js (backend)
- Конфігурація з env-змінних, а не з констант у коді.
- Централізована обробка помилок; не віддавати клієнту стек-трейси.
- Логування через логер проєкту, без персональних даних у логах.

## PHP
- PSR-12, `declare(strict_types=1);` якщо проєкт так робить; типи параметрів і повернення.
- Laravel/Symfony: валідація через Request/Validator, запити через ORM/Query Builder.

## Python
- PEP 8, type hints для публічних функцій, f-рядки.
- Без голого `except:`; ловити конкретні винятки.
