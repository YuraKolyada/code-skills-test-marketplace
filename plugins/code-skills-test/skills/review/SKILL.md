# Рев'ю змін

Перевір зміну так, ніби ти розробник, якого розбудять уночі, коли вона зламається. Розробник цей код більше не перевірятиме — твоє рев'ю єдине.

Порядок важливості: **працює правильно → безпечно → доступно → у стилі проєкту → протестовано → швидко → без зайвого.**

## 1. Спершу зрозумій

- Що перевіряти: те, що назвала людина (незбережені зміни, гілка, PR, файли). Нічого не названо — незбережені зміни, а якщо їх немає — останній коміт.
- Прочитай diff, а потім код навколо: хто викликає змінені функції, що вони викликають, тести, переклади.
- Зміна може зламати код, якого не торкалась: якщо змінилась сигнатура, повернене значення чи поведінка — знайди всі виклики.
- Правила репозиторію (конфіги лінтерів, CONTRIBUTING.md, CLAUDE.md) — головні. Загальні правила, коли в репозиторії своїх немає, — у `references/` цього скілу: `style.md`, `security.md`, `accessibility.md`, `review-checklist.md`.
- Запусти лінтер, typecheck і тести проєкту на змінених файлах, якщо вони є. Їхні помилки — теж знахідки.

## 2. Що шукати

1. **Помилка:** неправильний результат, падіння, пропущений крайній випадок (порожньо, нуль, останній елемент, часові пояси, округлення), зламаний виклик, текст доданий не в усі мови.
2. **Безпека:** секрети в коді, неекранований HTML, склеєні SQL-запити, ввід у shell-команди, відсутня перевірка вводу чи прав доступу, `target="_blank"` без `rel`, секрети в клієнтському коді, втрата даних (проковтнуті помилки, запис без транзакції).
3. **Доступність** (усе, що бачить користувач): немає `alt` чи `label`, `div` з `onClick` замість `button`, не працює з клавіатури, прибраний фокус, слабкий контраст, інформація тільки кольором, пропущені рівні заголовків.
4. **Стиль проєкту:** порушення правил лінтера/форматера, патерни не як у сусідньому коді, нова бібліотека чи підхід там, де в проєкті вже є свій, налагоджувальний код (`console.log`, `var_dump`), закоментовані блоки.
5. **Немає тесту:** нова ризикована логіка (розгалуження, гроші, авторизація, запис даних, виправлення бага) без тесту, якщо в проєкті тести є. Один добрий тест, не покриття.
6. **Швидкість:** запит у циклі, важкі зображення без розмірів і lazy-завантаження, важка бібліотека заради дрібниці.
7. **Зайве:** мертвий код, опції, які ніхто не просив, власна реалізація того, що вже є в репозиторії (вкажи шлях), майже-копії, які треба міняти разом.

## 3. Перевір себе перед звітом

- Кожна знахідка — з конкретним випадком: «ось такий ввід / ось така ситуація → ось такий поганий результат». Немає випадку — немає знахідки.
- Перечитай рядки й переконайся: виклик існує, значення справді може бути порожнім, код справді не використовується.
- Пропонуй найменше виправлення, яке працює. Без «варто розглянути» і смакових зауважень.

## 4. Звіт

Мовою людини (за замовчуванням українською), короткими реченнями, без жаргону. Технічний термін пояснюй при першій появі.

Почни з **«Що робить ця зміна:»** — 2–3 речення.

Далі знахідки трьома групами (порожні пропускай), нумерація наскрізна, щоб людина могла сказати «виправ 2 і 5»:
- **Треба виправити:** помилка, безпека, доступність, що блокує користувачів, падіння перевірок.
- **Варто виправити:** порушення стилю проєкту, ризикований код без тесту, помітна повільність, дублювання.
- **Дрібниці:** невеликі покращення.

Кожна знахідка — заголовок і місце (`шлях/файл.tsx:12-18`), далі чотири пункти по 1–2 речення:
- **Що це:** що робить цей код.
- **Проблема:** що піде не так і коли.
- **Як виправити:** найменше виправлення (можна з коротким фрагментом коду).
- **Якщо не виправити:** що відчує користувач чи компанія.

Наприкінці:
- **Висновок:** «Можна публікувати.» або «Спершу виправити 1 і 3.»
- **Не перевірено:** один рядок, якщо щось важливе перевірити не вдалося.

Нічого не знайдено: «Що робить ця зміна:», потім «Усе гаразд, можна публікувати.» і один рядок про те, що саме перевірено.

Код не змінюй. Наприкінці запропонуй: «Виправити знайдене?»
